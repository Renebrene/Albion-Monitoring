# CHANGELOG

Ветка `feature/postgres-core` — этапы работ 2026-10. Каждая строка =
коммит в репозитории.

## 2026-10

### PostgreSQL-фундамент (`d71078b`, `6943e49`)

- Схема `core` + `monitoring` (Alembic `0001`), роль `albion_app`, RLS
  `tenant_isolation`, функции `core.current_legal_entity_ids()` /
  `core.is_group_admin()`.
- SQLAlchemy Core + psycopg 3 как второй бэкенд (`DB_BACKEND=postgres`) при
  неизменном API и SQL приложения; SQLite остаётся точкой отката.
- Перенос SQLite → PostgreSQL (`migrate_sqlite_to_pg.py`) с отчётом,
  контрольными суммами и `--dry-run`/`--truncate`.
- Тесты: схема, RLS, идемпотентность миграций, полный ролевой прогон
  приложения на PostgreSQL.

### Доступ: сессии, аудит, роль/активность из БД (`aa1f394`)

- Серверные сессии с сроком и отпечатком токена; JWT привязан к сессии
  (`session_id`, `token_version`, `legal_entity_id`).
- Отзыв доступа: выход закрывает свою сессию, смена пароля отзывает все сессии
  и поднимает `token_version`, блокировка пользователя действует сразу; роль,
  активность и юрлицо читаются из БД на каждом запросе.
- Журнал `audit_log`: вход/отказ/блокировка, выход, смена пароля, настройки,
  задания; запись через SAVEPOINT — неудача аудита не откатывает транзакцию
  (в PostgreSQL молча превращала COMMIT в ROLLBACK).
- Справочники адресов закрыты токеном; PostgreSQL-сессия в UTC; адаптер
  воспрещает коммит прерванной транзакции.
- Alembic `0002`; SQLite-миграция v3 + репетиция на копии рабочей базы.

### Юрлицо в сессии и RLS (`df1819b`)

- Активное юрлицо хранится на серверной сессии; переключение — без выпуска
  нового JWT (`POST /api/session/legal-entity`), юрлицо уходит в RLS-контекст.
- Режим «Все юрлица» для группового администратора (сводный просмотр, создание
  запрещено до выбора конкретного юрлица).
- SQLite v4 (`legal_entity_id` у рабочих таблиц, `addresses.shared`,
  `user_entities`), аудит `auth.entity.switch`.

### Юрлица и доступ в админке (`57a1fd8`)

- Раздел «Юрлица группы»: создание, переименование, выключение/включение
  (удаления нет — данные сохраняются); защита от выключения последнего
  активного юрлица и юрлиц, оставляющих пользователей без доступа.
- Редактор доступа пользователя: юрлица, роль, основное юрлицо; защита
  «в группе остаётся хотя бы один администратор»; список пользователей и смена
  пароля ограничены областью видимости.
- Восстановление отсутствующих строк членства при входе; Alembic `0003`.

### Конструктор ролей (`4a0d806`)

- Каталог возможностей в коде (`permissions.py`), роль = возможности +
  рабочее место (страница) + область данных («всё юрлицо» / «только свои»).
- Системные роли восстанавливаются из кода и защищены; свои роли создаются с
  нуля или копированием.
- Все проверки эндпоинтов переведены на возможности; внутренние ветки
  «директор/сервис» — на рабочее место.
- Область «только свои» фильтрует ленты и списки по автору.
- SQLite v5, Alembic `0004`; E2E-проверка своей роли (403/200 по возможностям).

### Типы заданий (`f45168b`, `f4ee7dc`)

- Типы с до пяти доп. полей (текст, число, дата, список) и валидацией при
  создании; системный тип «Обычное задание»; состав полей используемого типа
  неизменяем.
- Раздел «Типы заданий» в настройках; селект типа и динамические поля в
  модалках создания (админ, директор); тип и значения полей на карточках.
- Excel-экспорт: колонка «Тип задания» + по колонке на доп. поле; в списке
  задач фильтр по типу.
- SQLite v7, Alembic `0005`.

### Переходы workflow (`b56e8c5`)

## Известные ограничения

- Изоляция юрлиц по чтению обеспечивается RLS и работает только на
  PostgreSQL; в SQLite ограничена область создания и списка пользователей.
- Роль назначается одна на все юрлица пользователя (модель `user_entities`
  уже допускает разные — требуется расширение UI).
- Excel-экспорт не выгружает вложения.
- Интеграция с Альбион.Диском (полные файлы на Диске, локальные previews,
  скачивание/загрузка по токену) — запланирована.
- Развёртывание на VPS (PostgreSQL в Docker, Caddy, тоннель, бэкапы) —
  инструкция в `app/DEPLOYMENT.md`, фактически не выполнено.
