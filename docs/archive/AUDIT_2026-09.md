# Albion Monitoring — техническая документация

> Обзор подготовлен по исходникам приложения в `app/` и статическому чтению интерфейсов. Это не подтверждение runtime/браузерного тестирования. В проекте есть локальные данные и незакоммиченные изменения — не пересоздавайте БД и не запускайте seed-скрипт без отдельной резервной копии.

## 1. Назначение и возможности

Веб-приложение для мониторинга рекламных экранов/адресов и координации командных работ. Основные сценарии:

- вход, JWT-аутентификация и журнал пользовательских сессий;
- адресный справочник с фильтрами города, производителя и текстовым поиском;
- создание и просмотр мониторингов/отчётов, лента событий и Excel-экспорт;
- фото- и видеовложения с ограничениями размера, обработкой изображений и настройками загрузки;
- отдельные отчёты Экипажа и комментарии Руководителя;
- задачи: создание, редактирование, вложения, комментарии, история статусов, отправка на проверку, утверждение, возврат на доработку, закрытие и скрытие;
- интерфейсы администрирования пользователей/настроек, директорская лента и ролевые страницы.

## 2. Архитектура и стек

Монолитное приложение: API, HTML-страницы и основная бизнес-логика собраны в одном FastAPI-модуле. Браузерная часть — Jinja2-шаблоны и vanilla JavaScript/CSS без обнаруженного frontend-сборщика.

| Слой | Реализация | Основные файлы |
|---|---|---|
| HTTP/API и страницы | Python 3.11, FastAPI, Pydantic | `app/app.py` |
| HTML | Jinja2 | `app/templates/*.html` |
| Клиент | Vanilla JS, CSS | `app/static/*.js`, `app/static/style.css` |
| Данные | SQLite, `sqlite3`, контекст `get_db()` | `app/database.py`, `data/monitoring.db` |
| Аутентификация | JWT/HS256 (`PyJWT`), bcrypt | `app/auth.py` |
| Медиа | multipart, Pillow, legacy uploads + optional private mount | `app/app.py`, `UPLOADS_DIR`, `PRIVATE_MEDIA_DIR` |
| Экспорт | OpenPyXL | `app/app.py` |
| Runtime | Uvicorn; контейнерный Gunicorn + Uvicorn workers | `app/Dockerfile`, Compose-файлы |

### Структура

- `app/app.py` — маршруты страниц и API, модели запросов, обработка медиа, задачи/воркфлоу, экспорт.
- `app/database.py` — пути БД и загрузок, открытие SQLite-соединений, создание таблиц, облегчённые schema-изменения, настройки.
- `app/auth.py` — пароль, выпуск/проверка JWT, проверки ролей и псевдонимов ролей.
- `app/role_capabilities.py` — декларативная модель возможностей новых ролей.
- `app/init_db.py` — отдельный seed пользователей и импорт адресов из CSV; выполнять только осознанно.
- `app/templates/` — страницы входа, клиента, сервера, задач, админки, директора, экипажа, руководителя и общий ролевой интерфейс.
- `app/static/` — клиентские сценарии по страницам; `common_cards.js` содержит общие карточки.
- `app/requirements.txt` — закреплённые версии Python-зависимостей.
- `data/` и `uploads/` в корне проекта — постоянные пользовательские данные; Compose монтирует их в контейнер.

## 3. Поток запроса и pipeline

1. Браузер получает HTML по page-route; FastAPI рендерит соответствующий Jinja-шаблон.
2. Шаблон загружает общий CSS и страницу/роль-специфичный JS из `/static`.
3. JS отправляет запросы на `/api/...`; защищённые API ожидают `Authorization: Bearer <JWT>`.
4. Роут проверяет пользователя/роль, валидирует Pydantic-вход и выполняет SQL через `get_db()`.
5. Контекст SQLite фиксирует транзакцию при нормальном выходе и откатывает при исключении.
6. Медиа проходит прежнюю валидацию; без `PRIVATE_MEDIA_DIR` загружается в `UPLOADS_DIR`, а при включённом параметре — в выделенный private mount. Ссылки сохраняются в БД и всегда выдаются через JWT-защищённый endpoint Monitoring.
7. Для Docker Compose образ собирается из `app/`, внутри слушает порт `8000`, наружу по текущей конфигурации публикуется `18000`; данные должны оставаться во внешних bind mounts.

Схематично:

```text
Browser -> FastAPI page -> Jinja template -> page JS/CSS
Browser -> /api/* -> JWT/role check -> SQLite + legacy/private media roots -> JSON
Compose -> Docker image -> Gunicorn/Uvicorn :8000 -> host :18000
```

## 5. API

Фактические маршруты объявлены в `app/app.py`. `Auth` в таблице означает Bearer JWT. Требования указаны по текущим проверкам кода; «авторизованный» не подразумевает любой конкретный ролевой профиль. Тела запросов — JSON, если явно не указано multipart.

### Авторизация, пользователи и настройки

| Метод и путь | Доступ | Назначение / вход |
|---|---|---|

Некоторые endpoint проверки используют `require_role`/`require_any`, поэтому фактические полномочия надо сверять по конкретному handler при изменении API. Таблица краткая, не замена OpenAPI схемам.

## 6. Основные backend-функции и модель данных

Важные функции `app/app.py`:

- `compress_image()` — переводит фото в JPEG, уменьшает размер/качество.
- `upload_media()` — проверяет расширение, настройки и размер, сохраняет временный файл.
- `create_report()`, `create_crew_report()`, `send_monitoring()` — создают мониторинговые записи и связи медиа.
- `get_task_for_workflow()`, `add_task_status_history()`, `set_task_workflow_status()` — читают задачу, фиксируют историю и обновляют workflow-статус.
- `complete_task()`, `approve_task()`, `rework_task()`, `close_task()` — операции переходов состояния.
- `director_feed()`, `get_unified_feed()` — формирование лент; `export_excel()` — выгрузка.

`database.py` объявляет таблицы пользователей/сессий, адресов, отчётов и медиа, отчётов/комментариев Экипажа, задач и настроек; включает внешние ключи и базовые индексы. `get_db()` включает SQLite foreign keys, commit/rollback и закрывает соединение. В `auth.py` пароли хэшируются bcrypt, JWT подписывается HS256 со сроком действия 7 дней.

### Важное замечание о схеме

Рабочая БД проекта содержит таблицы/поля задач workflow (например, `workflow_status`, `created_by_role`, `task_status_history`, `comments`), которых нет в исходном `CREATE TABLE tasks` и базовой схеме `database.py`. Значит, имеющаяся база пережила дополнительные изменения, не описанные полностью в воспроизводимой схеме/миграциях. Перед развёртыванием на чистой БД обязательно восстановить полный путь миграций и прогнать тест на копии БД; текущий запуск может вызвать `init_schema()` и частично изменить схему.

### Выполненные исправления по QA

- **Excel export:** клиент передаёт Bearer-токен, обрабатывает API-ошибки и сохраняет XLSX Blob; city/manufacturer/date filters передаются endpoint-у и применяются параметризованными запросами к обоим листам.
- **Logout:** общий `static/auth.js` делает `POST /api/logout`, затем в `finally` очищает localStorage и перенаправляет. Подключён к страницам client/server/tasks/admin/director/crew/head и общему role UI.
- **Video filename detection:** некорректные regex в client/admin/director приведены к стандартному `\\.`.
- **Health:** добавлен публичный минимальный `GET /healthz`; Compose и Render health checks используют его.
- **Configuration/build context:** JWT требует явный `JWT_SECRET` длиной минимум 32 символа, без известного fallback. Compose configs теперь требуют обязательную переменную `JWT_SECRET`; Render требует задать её в dashboard, потому что deploy config не задаёт значение. Добавлен `.dockerignore` для секретов, repo metadata, баз, uploads, архивов и локальных файлов; `.env.example` использует ожидаемое имя ключа.
- **Regression tests:** `app/tests/test_smoke.py` (30 API/workflow/storage tests) + `app/tests/test_maintenance_cleanup.py` (5 cleanup safety tests); full suite: 35 tests passed. запуск `uv run --with-requirements requirements-dev.txt python -m unittest discover -s tests -v`; тесты изолируют БД/uploads до импорта приложения и удаляют временный каталог после suite.
- **Address results:** `/api/addresses` ограничивает `limit` диапазоном 1–1000.
- **Общие настройки администратора:** в одной панели сгруппированы переключатели фото/видео, квоты и пользователи (список логинов/ролей, создание аккаунта, установка нового пароля). Defaults: фото 10 MiB, видео 100 MiB, total uploads quota 0 (без лимита); доступны отдельные per-file values и общая GiB quota, ZIP-поля не добавлялись. `0` для per-file снимает настраиваемый предел, однако действует hard safety cap 100 MiB. Текущие passwords не читаются/не показываются — хранится только bcrypt hash.

### Защищённая доставка медиа

По выбранной политике прямой публичный `/uploads` mount снят. Файлы выдаёт только `GET /api/media/{filename}` после Bearer JWT-проверки, filename ограничен basename и whitelist расширений, проверяется разрешённый путь и файл, ответы `private, no-store` и `nosniff`. Все сохранённые media records остаются без изменений; backend формирует API media URL. Общий `static/media.js` добавлен на все приложения: он авторизует загрузку через fetch, преобразует ответ в Blob URL и освобождает object URL при удалении DOM элемента/выгрузке; старые `/uploads/...` поля нормализуются в новый endpoint. Bearer не передаётся в query string.

Опционально новые фото/видео можно записывать в `PRIVATE_MEDIA_DIR` — отдельный private directory под фактическим `ALBION_DATA_DIR` Albion Files, но обязательно вне его публичном `uploads/`. Это local filesystem mount, а не интеграция с публичными ссылками/API Albion Files. Проверить фактический `ALBION_DATA_DIR` надо по unit/container env работающего экземпляра, а не выводить из репозитория. Создать выделенного Linux service user/group и directory permissions/ACL так, чтобы оба приложения получили доступ только к этому каталогу; не используйте Albion Files web login/API key — они не дают отдельного filesystem ACL. Само приложение не создаёт пользователя/каталог и не меняет права; если заданный mount недоступен, upload завершается 503 без fallback в legacy `UPLOADS_DIR`. В Docker добавьте bind mount только этого каталога и `PRIVATE_MEDIA_DIR` в фактически используемый Compose-файл. Новые storage keys получают префикс `pvt_`, старые файлы без него продолжают читаться из прежнего `UPLOADS_DIR`; перенос старых медиа не выполняется. Общая quota usage включает оба root. Создание папки, выдача прав, выбор активного data root и монтирование должны быть выполнены оператором после backup.

Это меняет прямые старые ссылки: bookmarks/external links вида `/uploads/file.jpg` теперь не обслуживаются (404); внутри приложения все роли должны входить, чтобы увидеть медиа. Видео загружается целиком в Blob и не использует HTTP range streaming, поэтому большие клипы могут потреблять больше памяти — оптимизировать streaming, если browser QA выявит проблему.

### Выполненные дальнейшие проверки и инструменты

- **SQLite migrations:** additive versioned миграции v1/v2 создают workflow/comment schema и добавляют прежние soft-hide/original-filename поля/индексы. Тесты покрывают fresh init, upgrade legacy fixture, сохранение legacy rows и idempotent повтор. На реальную БД миграции не запускались.
- **Task workflows:** isolated API tests проверяют service `open→pending_review`, admin `pending_review→completed`, историю, invalid transition, forbidden role и 404. Исправлен найденный access gap: director approve/rework теперь ограничены задачами, созданными директором; директорские алиасы роли тоже проверяются через base role.
- **Temp cleanup:** новый CLI `app/maintenance_cleanup.py`, default dry-run. Только regular non-symlink `temp_*`/`pvt_temp_*` старше 7 дней и не referenced в media tables или JSON comment fields могут быть кандидатами. Можно явно передать private root через `--private-uploads`; корни проверяются на symlink/overlap и блокируются отдельно. Hidden entries тоже считаются ссылками; missing schema/malformed JSON fail closed. Удаление только с `--apply`, explicit `--db`/`--uploads`, re-scan и quota locks. Ни к реальным paths, ни к пользовательским данным utility не запускалась.
